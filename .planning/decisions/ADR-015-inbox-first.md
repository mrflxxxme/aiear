# ADR-015 — Inbox-first архитектура захвата

## Контекст
Изначальная модель F3 предполагала доставку мысли «в destination» (Obsidian/календарь/
Telegram) как терминальную операцию: провал интеграции = провал фиксации. Фаундер
(grill 2026-07-07 §2.3, §3.1) предложил встроенное хранилище заметок как «фазу 0».
Локальное хранилище и так полу-закладывалось в F5 (история) — но как вторичная фича,
а не фундамент.

## Решение (ратифицировано фаундером)
1. **Каждая захваченная мысль СНАЧАЛА персистится во встроенный inbox приложения**
   (локальная шифрованная БД). Захват не может быть потерян из-за отсутствия,
   недоступности или ошибки интеграции. Inbox = встроенные «Notes» приложения,
   полноценный must-destination.
2. **Destination'ы — это экспорты/пропагации из inbox**, асинхронные и повторяемые
   (retry-очередь, идемпотентность по `thought_id`).
3. **Must-набор гейта MVP-0 (F3):** Share/Markdown · системный календарь/напоминание ·
   Telegram · Notes (inbox). **Obsidian — should**: реализуется в F3 (SAF-запись .md
   + URI-fallback), но его блок не держит гейт волны.
4. Локальное хранилище переезжает из F5 в **фундамент F1** (F1 создаёт inbox-персистенцию;
   F5 сохраняет за собой историю-UI, поиск и облачный sync поверх готового стора).

## Последствия
- F1: + Room/SQLCipher-стор и статусная модель мысли (captured → structured → exported).
- F3 упрощается до «экспортёров» с единым интерфейсом `Destination` и retry-очередью;
  частичные провалы не теряют данные.
- F6 (offline) получает готовую персистенцию бесплатно — очередь ре-транскрипции
  живёт в том же сторе.
- Ретеншен-риск выноса Obsidian из must компенсируется тем, что inbox сам является
  «вторым мозгом» первого уровня; Obsidian-экспорт остаётся в объёме MVP-0.

## Альтернативы (отклонены)
- **Destination-терминальная модель** — потеря мысли при провале интеграции, связность F3 с гейтом волны.
- **Интеграция с «системными заметками» Android** — единого API заметок в Android нет; покрывается Share-intent.
