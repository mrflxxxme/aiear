# ADR-012 — Модель аутентификации: аноним → привязка RF-OAuth

## Контекст
Модель идентичности нигде не была определена, при этом без неё не реализуемы F5
(`/v1/sync` — чьи данные?), S4/M5 (entitlement привязан к аккаунту) и весь биллинг.
Auth — tripwire-категория (ADR-011 D2): решение обязано пройти через фаундера.
MVP-0 бесплатен и позиционируется «без карты, ноль трения» (ADR-005) — принуждать
к логину до получения ценности нельзя; activation >40% — гейт волны (ADR-008).

## Решение (ратифицировано фаундером, grill 2026-07-07 §1.3)
1. **MVP-0:** анонимный **device-token** — клиент при первом запуске получает от
   backend непрозрачный токен устройства (UUID + подпись), все данные привязаны к нему.
   Ноль трения на онбординге, регистрации нет.
2. **MVP-1:** опциональная **привязка аккаунта VK ID или Яндекс ID** (RF-провайдеры
   OAuth). Привязка сливает device-scope в account-scope: entitlement и sync становятся
   мультидевайсными. Требуется для покупки подписки (биллинг ↔ восстановимая идентичность).
3. Миграция device→account — односторонняя операция слияния на backend; при конфликте
   данных действует LWW-политика F5.

## Последствия
- Backend-контракт (`specs/_contracts/openapi.yaml`): все `/v1/*` принимают
  `Authorization: Bearer <device-token|account-token>`; схема токенов едина.
- Таблицы БД проектируются сразу с `owner_id` (device или account) — миграция без
  перекройки схемы.
- Потеря устройства до привязки аккаунта = потеря данных: честно указать в UI
  (F4-онбординг) и подтолкнуть к привязке в MVP-1.
- `reviewer-security` проверяет: токен непрозрачен, не содержит ПД, TLS-only.

## Альтернативы (отклонены)
- **VK/Яндекс ID с самого начала** — трение на онбординге free-продукта, удар по activation.
- **Телефон + OTP** — стоимость SMS, ещё один внешний контракт/секрет.
- **RuStore-аккаунт как идентичность** — привязка к одному стору, iOS-волна V1 остаётся без идентичности.
