# Judge-панель — оптимальность на широких форках (ADR-011 D5)

Большинство форков — один проход (быстро, дёшево). **Широкий форк** заслуживает judge-панель: сгенерь N независимых подходов, роль `evaluator` ранжирует по фиксированной рубрике, берёшь победителя + прививаешь лучшие идеи проигравших. Дорогая разведка только там, где окупается.

## Когда триггерить (критерии широкого форка)

Панель — только если **все три** держатся:

1. **Форк agent-owned** (не эскалирован — см. [`escalation-policy.md`](./escalation-policy.md)). Эскалированные идут к фаундеру, не к панели.
2. **Пространство решений реально широкое** — выбор архитектуры / алгоритма / схемы / data-flow, где существуют материально разные дизайны (не «какое из двух эквивалентных написаний»).
3. **Blast-radius высок** — выбор трудно откатить позже (ставит схему, публичный-ish seam, кросс-контекст-контракт, нативный паттерн фона) ИЛИ доминирует корректность/стоимость/перформанс фазы.

Любой ложен → один проход с рекомендованным дефолтом. `planner` флагует широкие форки в `PLAN.md` (`wide_fork: true`), чтобы runner знал звать панель.

## Протокол

1. **Генерь** N независимых подходов (дефолт **N=3**; N=2 для low-stakes, N=4 для схемы/контракта, которую менять очень дорого). Каждый — cold (без подглядывания в другие), чтобы расходились.
2. **Судья** — роль `evaluator` скорит каждый подход по рубрике ниже. Refute-by-default: подход должен *заслужить* оценку.
3. **Выбор + прививка** — топ-подход; явно вложи любую превосходящую суб-идею проигравших (назови, что привито).
4. **Запись** — `log_decision.py --kind arch` (широкие форки почти всегда архитектурны) с победителем, скорами, что привито. Пиши/аттач ADR, если ставит прецедент.
5. **Emit evidence** (D3 tie-in) — прогон панели пишет `evidence/judge_panel_<fork>.json` (verdict `PASS` = победитель выбран с обоснованием; скоры + стоимость). Объяви в `evidence/manifest.json`, чтобы `ci-evidence` подтвердил, что оптимизация реально прогнана против смёрженного коммита.

## Рубрика (фиксированный приоритет)

Evaluator ранжирует лексикографически — низший критерий ломает ничьи только среди равных по высшим:

1. **Корректность** — реально решает задачу, держит edge-cases, сохраняет инварианты (напр. биллинг `total == SUM(steps)`; на устройстве — выживает screen-off/Doze).
2. **Безопасность / целостность** — секреты/ключи, **ФЗ-152/242 (ПД россиян только RF-облако)**, отсутствие новой attack-surface, data-integrity, нативные баны ADR-002.
3. **Простота / поддерживаемость** — минимум концептуальной поверхности, ложится на существующие паттерны (ADR), читаемо через год.
4. **Стоимость** — токен/compute/infra + dev-time (уважает `cost-budget.yaml`); на устройстве — батарея (wake-word ≤3%/ч).
5. **Перформанс** — латентность/throughput (STT-стрим <2 сек, активация <1 сек), только где важно.

> Корректность и безопасность — гейты, не размены: подход, проигравший на #1 или #2, не может победить простотой/скоростью.

## Cost-дисциплина

Панель множит токен-спенд на форке (~N×). Оправдана только критерием #3 (высокий blast-radius). Runner считает спенд панели против per-run budget (`cost-budget.yaml`); если бюджет тесен, деградируй N=3→N=2 прежде чем скипать панель на реально широком форке.

## Роли

`evaluator` (LLM-as-judge, ADR-006 ростер) скорит. N подходов генерит релевантная impl-роль (`android-engineer` / `backend-engineer`) или, для чистых дизайн-форков, `architect`. Нативные форки фона — подключай `native-spike-debugger` как одного из генераторов (agent-device-петля). Спавн ролей — через `scripts/autonomy/load_role.py` + `Agent` tool.
